# Collision weights and hard-filter comparison — 11/11

Fixed setup: 50 planar double-integrator robots, GNN–CP–autodiff, required r = 21, 320 future steps, dt = 0.05 s (16 s), 5 optimization updates, seed 42, acceleration noise 0.1 m/s², R = 3 m, acceleration norm ≤ 1 m/s². Starts and independently assigned goals are copied exactly from the saved 11/09 experiment. Goal arrival remains a soft cost. All cost settings except collision weight are fixed.

Robot radius is 0.20 m: a physical overlap means center separation < 0.40 m. The hard filter requires ≥ 0.45 m, including motion between waypoints, using the constant-acceleration dynamics. Counts below are distinct robot pairs that violate the threshold at any time; they are not numbers of frames or simultaneous collisions.

CP-only acceptance is explicitly enabled only for part 1 of this experiment. Part 2 uses the default joint CP + collision filter. CP-selected means the selected trajectory meets the predicted hard-graph CP threshold at every sampled future waypoint. This is not an unconditional robustness guarantee under adaptive trajectory search.

## Reproduce

Run from the `jax_GNN` directory with CUDA available. Replace `50` with `100` for the other population. Use separate output folders for each policy.

```bash
JAX_PLATFORMS=cuda .venv/bin/python -m planning.tune_collision_weight \
  --particles 50 --legacy-cp-only --weights 1000 6900 30000 100000 \
  --output reports/trials/11-11/large_particle_collision_trials/particles_50/cp_only
```

For the hard filter, omit `--legacy-cp-only`, use `--weights 10 BEST_WEIGHT`, and write to `particles_50/joint_filter`. Weight 10 is automatically included. Each `weight_*.json` contains the full configuration, geometry, parameters, selected trajectory (or null), controls, velocities and acceptance report.

To evaluate both rules on exactly the same candidate populations in one run:

```bash
JAX_PLATFORMS=cuda .venv/bin/python -m planning.tune_collision_weight --particles 50 --weights 6900 30000 100000 --output reports/trials/11-11/large_particle_collision_trials/particles_50/joint_filter --compare-cp-only-output reports/trials/11-11/large_particle_collision_trials/particles_50/cp_only
```

## Best selected result and runnable scenario

The best completed CP-only result has 262 physical-overlap pairs at weight 1000 with 100 particles. This is the best tested selection, not a global optimum. `best_result_reference.json` points to its full saved trajectory and parameters. `best_weight_scenario.json` preserves the exact geometry and uses this weight with the hard collision filter enabled. It therefore returns no feasible trajectory if no candidate satisfies both filters; it never falls back to the colliding CP-only result.

```bash
JAX_PLATFORMS=cuda .venv/bin/python -m planning --scenario reports/trials/11-11/large_particle_collision_trials/best_weight_scenario.json --robots 50 --particles 100 --steps 320 --iterations 5 --methods gnn_cp_autodiff --output reports/trials/11-11/large_particle_collision_trials/best_weight_joint_rerun.json
```

## Previous 15-particle comparison

The earlier 15-particle CP-only sweep on the same geometry selected weight 6900 with 270 physical-overlap pairs and 310 clearance-violating pairs. That trajectory was also unsafe. This historical result is separate from the new 50/100-particle trials. A larger population can select a trajectory with more distinct overlapping pairs because the objective minimizes weighted penalty severity and other costs, rather than the count of distinct overlapping pairs.

## Resource handling

The first 100-particle optimization was killed with exit code 137 before saving a feasibility result. It is not counted as a no-feasible outcome. Memory pressure was suspected, but kernel OOM logs were unavailable. The retry evaluates base costs/gradients in batches of eight particles and constructs CP graphs in chunks of approximately 256, aligned with the checkpoint minibatch size. It retains all 100 particles, all 320 steps and five updates. Tests check costs, gradients, CP bound values and ordering against unchunked calculations. The 50-particle runs precede this scheduling change, so population timings also reflect different memory scheduling. See `resource_retry.json` for details.

The 100-particle trials test weights 10, 1,000, 10,000 and 100,000: the default, two intermediate values, and the best full 50-particle weight. The intermediate values test whether updated candidates improve on the initial-candidate ranking. Reproduce them with:

```bash
JAX_PLATFORMS=cuda .venv/bin/python -m planning.tune_collision_weight --particles 100 --weights 1000 10000 100000 --progress --output reports/trials/11-11/large_particle_collision_trials/particles_100/joint_filter --compare-cp-only-output reports/trials/11-11/large_particle_collision_trials/particles_100/cp_only
```

These finite trials do not establish that the scenario is infeasible. A no-feasible result means the candidates generated at that tested weight and optimization budget contain no trajectory that passes both filters.
